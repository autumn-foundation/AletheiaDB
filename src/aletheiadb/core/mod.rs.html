1//! Core primitives for AletheiaDB.
2//!
3//! This module contains the fundamental types and data structures that
4//! serve as the building blocks for the database engine.
5//!
6//! # Core Components
7//!
8//! - **[`graph`]**: Fundamental graph elements ([`Node`], [`Edge`]).
9//! - **[`id`]**: Strongly-typed identifiers ([`NodeId`], [`EdgeId`]) and ID generation.
10//! - **[`property`]**: Copy-on-write property system with [`PropertyMap`].
11//! - **[`temporal`]**: Bi-temporal primitives ([`Timestamp`], [`TimeRange`]) for tracking valid and transaction time.
12//! - **[`vector`]**: Vector embeddings and similarity metrics.
13//! - **[`interning`]**: String interning for memory-efficient storage of labels and keys.
14//! - **[`hlc`]**: Hybrid Logical Clock implementation for distributed timekeeping.
15//!
16//! # Why Interning?
17//! Strings like graph labels ("Person", "KNOWS") and property keys often repeat millions of times.
18//! Storing them as raw `String`s would be highly memory inefficient.
19//! Instead, the [`interning`] module maps these repeating strings to integers (IDs), reducing overhead
20//! and making comparisons as fast as an integer check.
21//!
22//! # Why Hybrid Logical Clocks (HLC)?
23//! In distributed systems, relying solely on wall-clock time can lead to ordering issues due to clock drift.
24//! Using purely logical clocks loses the human-readable concept of "when" something happened.
25//! The [`hlc`] module combines both: ensuring causal ordering for events while remaining tightly bound
26//! to the physical wall clock, bridging the gap between machines and human expectations.
